### 原Issue opening正文（历史要求原文）

## 背景

Issue #3 已确认当前 ASTRA/ns-3 将每个 `sim_send` 建成一个新 QP，并通过自动递增的 source port 参与原版哈希选路。依靠生成 100+ QP 碰撞出近似均衡是一条错误路线。真实 GPU/RDMA 通信更接近“少量 QP + 上层把流量分配到 QP 组”，因此需要一个显式、可审计且默认关闭的 QP 配置入口。

## 目标

- simulator frontend 只读取 bridge 已解析好的 `qp_bindings.csv`，按 `(src,dst,tag,size)` 使用指定 `source_port`；无配置时保持上游行为。
- QP 定义、QP 分组、`flow -> group`、4096B packet 对齐均分、source-port 搜索和 child send/tag 生成全部放在 bridge interface。
- 一条 logical flow 选择一个 QP group；组内每个 QP 对应一个大 child send，字节总和严格守恒，最大差不超过一个 4096B packet。
- 仍使用原版 QP hash、NIC/ECMP、packetization、ACK、PFC 和拥塞控制；禁止直接传 `path_id` 绕过哈希。
- 以 `docs/simulator/astra_ns3/QP_CONFIGURATION_REQUIREMENTS.md` 作为需求与可信性边界的 source of truth。

## 第一版边界

- 只支持确定性等权分配，不实现权重调度。
- 配置开启后严格匹配；缺项、重复 tag/port、端点不一致、端口越界或找不到目标路径的 hash preimage 时直接失败。
- 不修改 nested ns-3 的 `rdma-hw`、`rdma-queue-pair`、Qbb、switch 或拥塞控制代码。
- 本 issue 不实现 persistent QP reuse/message queue。相同 source port 的重新创建不等于跨 message 保留 PSN、ACK 和拥塞控制状态；需要该语义时另立独立 issue。

## 验收

- 2 GPU、5 path：`g3={q0,q1,q2}` 与 `g2={q3,q4}`，两条 flow 分别绑定 g3/g2，实际只产生 3/2 个 QP。
- 每条 flow 字节守恒，组内差不超过 4096B；后继操作等待全部 child 完成。
- trace/FCT 证明实际 source port 和原版 hash next-hop 与配置一致。
- 功能关闭时，补丁版与未修改上游在标准 smoke 的 FCT、trace 和 summary 一致。
- bundle 保存 simulator commit、binding、assignment 和实际路径证据，结果可重复生成。

关联 #3。旧分支 `codex/3-clos-alltoall-calibration` 仅作为探索档案，不作为新实现基线，也不整体合并。
