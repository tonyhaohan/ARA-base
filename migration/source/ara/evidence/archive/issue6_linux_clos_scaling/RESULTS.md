# 单层 Clos 扩规模结果：最大已测到32卡

今天新增11个配置，每个运行两遍，共22次正式性能运行。全部完成并通过独立验收，两遍完成时间逐纳秒一致。10个配置的理论差距低于8%；8卡、2交换机、四平行链路为8.36714%。32卡双链路出现可重复的PFC流控记录，不能称为完全无拥塞。

这完成了本轮代表性扩规模验证，不是全225组合、双层Clos、UBMesh或真实MCNF求解结果接入的完成声明。

## 固定条件与版本

- 每个有向卡对8,000,000字节，十进制8MB；全互发任务，不是Allreduce。
- 每条物理链路400Gbps、500ns传播延迟；小包4096字节；每条完整物理路径一个QP，即R=1；均匀分配。
- bridge固定为 `1d4f816a542f46ff0d1c99af6ce2d8b097822303`，ASTRA固定为 `181c7856ed77bac3be68495e2400752488df5e5a`，没有更新或调整核心源码。
- 实际ELF在运行前及结束后独立计算SHA256，仍为 `7f9db19d50dafbe8d371c9f64cbef8b9e7b27cb7794fb1c62e6be8956ade67f4`。
- 未调整ACK、拥塞控制、带宽、传播时延、包大小或求解算法。新增的只有外层运行、只读验收工具和研究记录。

N为卡数，M为并行交换机数，Q为每张卡到每台交换机之间的平行物理链路数。纯带宽理论时间始终为 `160*(N-1)/(M*Q)` 微秒；差距为 `(仿真/理论-1)*100%`。没有换用带协议开销的分母来降低差距。

## 两项必须保留的观察

### 8卡四平行链路略高于8%

8/2/4重复得到151.714μs，比理论140μs多11.714μs，差距8.36714%，超过8%目标约0.36714个百分点。字节、正式路由配置、校准路径和重复时间均通过核验；两遍PFC事件为0。结果既不删除，也不通过改带宽或协议参数修饰。

8/4/2具有相同的N和M*Q，纯带宽理论时间同为140μs，但实测148.855μs，比8/2/4少2.859μs。两者物理拓扑及完整路径数量不同，这只是一个后续诊断对照，尚未证明具体时间差由QP数量、排队或ACK中的哪一项造成。

### 32卡双链路出现PFC

32/2/2两份pfc.txt字节相同，SHA256 `38604fc1770b2d4336ebb3932319316f68bd74f586bec6899987bc5fd0b7a2b2`。每遍312条记录由156条收到暂停和156条收到恢复组成。记录集中在1241.436～1260.041μs；任务在1293.096μs完成。各节点/接口内暂停与恢复交替，最后均恢复。

服务器实际构建使用的 `extern/network_backend/ns-3/scratch/common.h:140-144` 将字段写为时间步、节点ID、节点类型、接口ID、收到的PFC类型；`qbb-net-device.cc` 的QbbPfc回调明确1为暂停、0为恢复。默认时间单位为ns，实际common.h没有修改Time分辨率。全部事件来自计算卡侧，覆盖31张卡的39个接口。源代码的缓冲阈值检查会触发流控，因此可确认该场景达到过PFC阈值。

不能把312条记录解释成312次暂停或312个丢包；也不能把跨接口的暂停区间相加当作任务延迟，因为它们可重叠，且日志不包含优先级队列编号。尚未定量拆分PFC对完成时间的贡献，不能用此现象解释没有PFC事件的8/2/4差距。

## 独立验收及资源

两个正式批次均得到 `PASS; 0 errors; 0 missing runs`。22次共核对41,184条FCT完成记录，以及22份独立校准中的41,184个QP逐跳路径。每张卡完成、字节守恒、精确均匀分配、版本指纹、原始日志和两遍相等性均通过。

研究记录的结构校验与全局图更新完成，相关19项测试通过。独立最终审阅再次对照22份原始summary与PFC，复算数量、资源指标并核对压缩包哈希，未发现数值错误或结论越界。

独立审阅后特别补充实际输入检查：正式qp_config的QPs/routes必须与校准相同，messages逐项对应children，每条FCT对应实际child端点/IP/端口/字节，且两遍qp_config字节相同。此为只读验收补强，不修改仿真输入。验收器在昨日8个rr案例复测通过，篡改路由接口、字节数、QP端口的纯内存负例均被拒绝。

跨运行校准trace原始字节不同的11条提示保留；每份文件均匹配其自身哈希并通过重新解析。正式性能案例未开全包trace，因此不能宣称已经逐包证明正式实验零丢包/零重传，更不是真实硬件测量。

22条包装命令的time-v耗时合计305.76秒，包含输入生成、校准和仿真，不包含人工分析和下载。最大MaxRSS为253,748KiB，约247.8MiB；这是GNU time报告的命令最大驻留内存指标，不是整机所有进程同时占用的总峰值。实验结束服务器约29GiB内存可用。本批内存不是瓶颈，但不能据此推断求解器、大型双层或UBMesh的内存需求。
